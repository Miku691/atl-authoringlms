Table: users

Mapping: auth.users → linked to student/instructor/staff via user_id

Stores authentication credentials and basic auth metadata. Used by auth-service only.

Mapping & Notes

  • users.id is referenced by student_service.user_id, instructor_service.user_id, and staff_service.user_id.
  • user_tenants allows a single user to belong to multiple tenants (useful for guest teachers or admins managing multiple schools).
  • All timestamps should be stored in UTC. Use appropriate indexes on username, tenants.code, and FK columns.

More About the service:-

  • The bootstrap admin is created without a tenant because the tenant does not exist yet, and is marked with a special status PENDING_TENANT_CREATION.
  • The bootstrap admin serves as the initial super-user who will later create and configure the tenant (school/college) during the onboarding flow.
  • Only essential details (name, email, phone, password) are collected, and the user is automatically assigned the SUPER_ADMIN role.
  • The system validates email uniqueness and ensures the SUPER_ADMIN role is available, then securely stores the user with hashed password.
  • After tenant creation, the system assigns the bootstrap admin to the newly created tenant and updates the account status to ACTIVE, enabling full login and management.
